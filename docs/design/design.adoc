= Time Traveler: Rust service design
:toc:
:toclevels: 2

The Rust service that replaces `src/*.js`: a member records roughly how long each day goes to each activity, an admin operates the member list. The frontend in `public/` stays as it is, so every route answers the JSON the Node version answers today. Storage moves from the Erawan Postgres add-on to MongoDB Atlas; sign-in stays on the Erawan auth add-on. The service deploys on Erawan first and moves off it later, one step at a time.

Rewritten 2026-11-08 against `src/*.js`, `public/app.js`, `public/admin/admin.js` and the crates named in section 6, and approved by Rux the same day. Decisions attributed to Rux are his; everything marked _proposed_ was mine and stands with that approval. Section 10 lists what was verified and what was not.

== Decisions

* Rust, modelled on `agent-memory` (Rux, 2026-11-07): Axum 0.8, Tokio, `rzlib-error`, `jiff`, `config`, `trait-variant`, the per-module clippy deny list and the model/storage/web split.
* MongoDB Atlas now, not Postgres first (Rux, 2026-11-07). Cluster `default.ysnnrsq.mongodb.net`, Bangkok. The storage model is designed for Mongo, not carried over.
* The domain model is Rux's (section 2.1). It has no `hidden` feature (Rux, 2026-11-07): `PUT /api/builtins/{key}` goes, `hiddenBuiltins` leaves `/api/state`, and `public/app.js` loses its hide toggle.
* The nine predefined activities are static data, not a type: `Activity` values with fixed ids, held in code (Rux, 2026-11-07). `sport` joined the first eight on 2026-11-10: one entry in `activities::PREDEFINED_NAMES` and one in `BUILTIN`, `ICONS` and the two `act.sport` translations of `public/`; its id follows from its name, so no stored document changed.
* The running session is application state, not a domain `TimeSession`: a domain `TimeSession` has ended (Rux, 2026-11-07).
* _Proposed._ Sign-in state lives in HMAC-signed cookies, not in collections: the member session, the admin session and the OIDC handshake. Section 4 defines the format. What changes against Node: a logout clears the browser that asked, not every device; disable and delete still take effect on the next request, because every request loads the `User`.
* The service runs as one instance (Rux, 2026-11-08), so the first admin's setup token and the login throttle are held in memory; no collection holds sign-in state of any kind. A restart while no admin exists prints a new setup link.
* _Proposed._ One running session per user is kept by a partial unique index on a `Running: true` marker, because a partial index cannot filter on an absent field (`$exists: false` is not allowed in `partialFilterExpression`; equality is). `Running` is a derived value held for the index, written in the same operation as `EndedAt` (article 9).
* _Proposed._ Starting a session is two writes with no transaction: end the running session and read its `EndedAt`, then insert the new one starting at that instant. A race loses on the unique index and retries. Only deleting a user runs a multi-document transaction.
* The wire model is today's JSON (bylaw 4). A new code is added only where Node answered no JSON at all (`not_configured`, `method_not_allowed`) or a 500 for a malformed request (`bad_body`); a Mongo failure stays `server_error`.
* Every model is its own type (article 10): domain `model.rs`, storage `storage.rs` (a document that converts to no valid domain value is refused), wire `web/*.rs`.

* `activities::PREDEFINED: [Activity; 9]`. Each id is `Uuid::new_v5(&NAMESPACE, name.as_bytes())` with one namespace UUID fixed in code, so the ids are stable and derivable, never typed by hand. `name` is the key the client translates (`sleep`, `nap`, …), `color` the colour `public/app.js` already assigns to that key. `PREDEFINED` is looked up by id and by name; nothing else distinguishes a predefined activity from a stored one. `activities::PALETTE: [&str; 6]` is `CUSTOM_COLORS` from `src/activities.js`.
* `activities::ICONS: [&str; 12]` (`star`, `book`, `music`, `heart`, `code`, `cart`, `home`, `pencil`, `leaf`, `chat`, `camera`, `film`) are the icons a stored activity may take (Rux, 2026-11-11): keys of the drawings in `public/app.js`, in the same order as its `CUSTOM_ICONS`. `DEFAULT_ICON` is `star`, the one drawing every stored activity had before. A predefined activity's `icon` is its own name, the key the client already draws it by, and is outside this list as its colour is outside the palette.
* `Timestamp` is `jiff::Timestamp`. Every instant the service writes is taken once per request (`Timestamp::now()` at the start of the facade call) and reused, as Node's one `now()` per transaction.
* `Activity::new(name, color, icon)` normalises nothing: the web layer trims, collapses runs of whitespace to one space and refuses an empty or over-long name before the domain sees it; the constructor refuses what still violates the comment. `TimeSession::new` refuses `ended_at < started_at` and a target outside the range.
* `PasswordHash` is a value type that parses and prints Node's `scrypt$N$r$p$salt$key` string and verifies a password against it (section 2.5).

=== Database

Database `traveler` on the Atlas cluster. Field names PascalCase; a `?` field is absent, not null, when it has no value. Ids are BSON UUID (binary subtype 4) through `bson::serde_helpers::uuid_1_as_binary` (feature `uuid-1`); timestamps are BSON `Date` (millisecond precision) through `timestamp_bson`, copied from agent-memory. Mongo enforces none of the references between collections; the service does.

* `OneRunning` is what keeps one running session per user, as Postgres' `time_sessions_one_running` did. `{ UserId: 1 }` with `partialFilterExpression: { Running: true }` indexes only the running documents, so a user has at most one. Stopping a session `$set`s `EndedAt` and `$unset`s `Running` in one update, so the two are never seen apart.
* `Identity` is a compound index over two fields of one array, which Mongo allows (one array per compound index); unique means no two users share an (issuer, subject).
* No TTL index: nothing stored expires.
* Indexes are created by `traveler-migrate indexes` before the first deploy and after any change, never by the service. At startup the service lists each collection's indexes once, in the background, and logs each missing name at Error; it serves either way.
* Document counts stay far under the Free cluster's limits (500 collections, 0.5 GB, 500 connections); the driver's pool is left at its default of 10 connections maximum.

=== Storage conversions

`storage.rs` holds one `serde` record per collection (`UserRecord`, `ActivityRecord`, `TimeSessionRecord`, `AdminRecord`), `From<&Domain>` into a record and `TryFrom<Record>` out of it. A record that converts to no valid value is refused: the read fails with code `corrupt_document`, logged at Error with the collection and `_id`, and the request answers 500 `server_error` (article 10; the data is repaired by hand, article 3).

[cols="1,2"]
|===
| Record | Converts to, or is refused when

| `UserRecord` | `User` + `Vec<Identity>`; refused when `Identities` is empty
| `ActivityRecord` | `Activity` + `Ownership`; refused when `Name` is not 1..40 scalar values, `Color` is not in the palette or `Icon` is not one of the icons; an absent `Icon` reads as `star`, so the documents written before icons need no migration, and a write always stores the icon
| `TimeSessionRecord` with `EndedAt` present and `Running` absent | `TimeSession` + owner; refused when `EndedAt < StartedAt` or `TargetSeconds` is outside `60..=86400`
| `TimeSessionRecord` with `EndedAt` absent and `Running: true` | `Running` + owner; same `TargetSeconds` rule
| `TimeSessionRecord` in any other combination | refused
| `AdminRecord` | `Admin`; refused when `Username` fails the pattern or `PasswordHash` does not parse (section 2.5)
|===

Migrated data has one known deviation: the Node version stored `target_seconds` as `targetMinutes * 60` with minutes in `1..=1440`, which is inside the range, and `activities.name` was trimmed and collapsed on the way in, so no existing row is expected to be refused. The import tool reports every refused row by table and id and writes nothing when any is refused (section 9).

=== Password hashes

Node's `admin.js` hashes with `crypto.scrypt(password, salt16, 64, { N: 16384, r: 8, p: 1 })` and stores `scrypt$16384$8$1$<salt base64>$<key base64>`. The Rust `PasswordHash`:

* parses the string into `N`, `r`, `p`, salt bytes and key bytes; refuses a `kind` other than `scrypt`, an `N` that is not a power of two, or an unparsable base64;
* verifies with `scrypt::scrypt(password, &salt, &Params::new(log2(N), r, p)?, &mut out)` where `out.len() == key.len()` (scrypt 0.12: `Params::new(log_n: u8, r: u32, p: u32)`; the output length comes from the buffer), then compares `out` with the stored key in constant time (`subtle::ConstantTimeEq`);
* hashes a new password with the same parameters (`log_n` 14, `r` 8, `p` 1, 16 random salt bytes, 64-byte key) and prints the same string, so the migrated admin signs in unchanged and a hash made by either version verifies in the other.

Password length is counted in UTF-16 code units (`password.encode_utf16().count()`), which is what JavaScript's `.length` counted, so the same passwords pass `10..=200` in both versions.

== Wire model

Today's JSON, as `public/app.js` and `public/admin/admin.js` read it. The one removed route is `PUT /api/builtins/{key}`, with `hiddenBuiltins` leaving `GET /api/state`; `public/app.js` loses `toggle-builtin`, `state.hidden` and the hide buttons in the same change.

An activity on the wire is a string key: a predefined activity is its name (`sleep`), a stored one is `c:` + its UUID in lowercase hyphenated form. `web/keys.rs` converts both ways: key → `Uuid` through `PREDEFINED` by name, or the `c:` prefix followed by exactly the 8-4-4-4-12 hexadecimal form (case-insensitive, as Node's regex); `Uuid` → key through `PREDEFINED` by id, or the prefix. Session ids and user ids on the wire are UUIDs in the same form; a path id in any other form answers 404 `not_found`, as Node's `isUuid` did.

Timestamps on the wire are UTC with exactly three fractional digits and a `Z` (`2026-11-08T03:04:05.678Z`), formatted with jiff's `%Y-%m-%dT%H:%M:%S%.3fZ`, which is what `Date.prototype.toISOString` produced. BSON `Date` carries milliseconds, so nothing is lost.

=== Routes

Every member route after `/api/config` requires the member cookie; every non-GET among them requires `X-CSRF-Token`. Every admin route after `/admin/api/login` requires the admin cookie, and every non-GET among them the CSRF header. Request bodies are JSON, at most 16 KiB.

|===
| Route | What it is for | Reads | Answers

| `GET /healthz` | Erawan's readiness probe: is the service up and can it reach the database | | `{ok: true}`; 503 `{ok: false}` when `ping` on the database fails or takes over 5 s
| `GET /api/config` | The login page asks which sign-in buttons to show before anyone is signed in | | `{providers: ["google","line","email"]}` when `auth` is configured, else `[]`; `devLogin: bool`

| `POST /admin/api/setup` | Create the first and only admin, with the one-time token from the link the service logged at startup | `{token, username, password}` | 201 `{ok: true}`, admin cookie set; 400 `bad_username`, `bad_password`; 409 `already_set_up`; 403 `bad_token`
| `POST /admin/api/login` | Admin sign-in with username and password; five failures lock the name for 15 minutes | `{username, password}` | `{ok: true}`, admin cookie set; 401 `bad_credentials`; 429 `{error: "locked", retryAfterSeconds}`
| `POST /admin/api/logout` | Sign the admin's browser out | CSRF | `{ok: true}`, admin cookie cleared

| `POST /admin/api/users/{id}/disable` | Lock a member out: they cannot sign in or call the API, and their running session ends now; their data stays | | `{user: UserView}`; 404 `not_found`
| `POST /admin/api/users/{id}/enable` | Lift the lock | | `{user: UserView}`; 404 `not_found`
| `DELETE /admin/api/users/{id}` | Erase a member and everything they recorded | | `{ok: true}`; 404 `not_found`

Views, with `null` where Node sent null:

* `SessionView`: `{id, activity, startedAt, endedAt, targetSeconds}`; `endedAt` null for the running session, `targetSeconds` null when none.
* `ActivityView`: `{key, name, color, icon, deleted}` (`icon` added 2026-11-11, a field Node never answered, so bylaw 4 holds).
* `UserView`: `{id, name, email, createdAt, disabled, disabledAt, lastActive, sessionCount}`; `disabled` is `disabledAt != null`; `lastActive` the greatest `StartedAt` of the user's sessions or null; `sessionCount` their count. Both come from one aggregation over `TimeSession` (`$match` the user ids, `$group` by `UserId` with `$max` and `$sum`), never stored (article 9).

Request validation, exactly as `api.js` and `admin.js` do it:

[cols="1,3"]
|===
| Field | Rule

| `targetMinutes` | absent, `null` or `0` → no target; otherwise a JSON integer in `1..=1440`, stored as seconds × 60; anything else → `bad_target`
| `activity` | a string that is a predefined name, or `c:` + UUID of a live activity of this user → else `bad_activity`
| `name` | a string, trimmed, runs of whitespace collapsed to one space; then 1..=40 Unicode scalar values → else `bad_name`
| `color` | used when it is one of the 6 palette strings; otherwise the palette entry at `(count of the user's activities, deleted included) mod 6`
| `from`, `to` | RFC 3339 timestamps with an offset or `Z`; the frontend sends `toISOString()` output
| `username` | trimmed, lowercased, then `^[a-z0-9._-]{3,32}$` → else `bad_username`
| `password` | 10..=200 UTF-16 code units → else `bad_password`; on login a password over 200 is simply wrong
| `token` | the string from the setup link's fragment; anything else behaves as an unknown token
| a body that is not JSON or not the expected shape | 400 `bad_body` (Node answered its 500 `server_error` page here; no client sends one)
|===

=== Errors

Every error answers `{error: <code>}`, plus `retryAfterSeconds` on `locked`:

[cols="1,1,3"]
|===
| Status | Codes | Source

| 400 | `bad_range` `bad_target` `bad_activity` `bad_name` `bad_username` `bad_password` `bad_body` | request validation
| 401 | `not_signed_in` `bad_credentials` | no or invalid cookie; wrong admin password
| 403 | `bad_csrf` `bad_token` `disabled` | CSRF header mismatch; setup token unknown, used or expired; dev-login of a disabled user
| 404 | `not_found` `not_configured` | unknown route, id or key; sign-in without `auth` settings
| 405 | `method_not_allowed` | a known path with another method (new; Node answered Express's HTML page)
| 409 | `running` `too_many` `already_set_up` | delete of the running session; 51st live activity; setup after an admin exists
| 429 | `locked` | 5 failed admin logins within the lock window
| 500 | `server_error` | a driver error or a 5 s timeout on a Mongo call (inside: `database`), a refused document (`corrupt_document`), any other defect; the inner code is logged, the wire sees `server_error` as it did from Node
| 503 | | `/healthz` only, with `{ok: false}`
|===

Inside the service every refusal is an `rzlib-error` `ErrorInfo` whose code is the wire code; `web/errors.rs` maps code to status in one `status_of` table, as agent-memory does, and logs the location trail, which never reaches the wire.

=== Cookies, CSRF, headers

* Cookie names: `__Host-tt_sid`, `__Host-tt_admin`, `__Host-tt_oidc` when the request is https, `tt_sid`, `tt_admin`, `tt_oidc` on plain http (local development). Attributes `HttpOnly; SameSite=Lax; Path=/`, `Secure` on https, `Max-Age` 30 days / 12 hours / 15 minutes, never `Domain` (Erawan's gate refuses a domain-scoped cookie, and the shared `erawan.app` domain is why). Clearing sets the same name with `Max-Age=0`.
* The request is https when `X-Forwarded-Proto` is `https` (Erawan terminates TLS; Node had `trust proxy`), else when the listener itself is TLS, which it never is here.
* Every state-changing request carries `X-CSRF-Token` equal to the `csrf` inside the signed cookie, compared in constant time (`subtle`). SameSite alone is not enough on the shared domain.
* Every response carries the headers `server.js` sets: `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self' https://fonts.googleapis.com; font-src https://fonts.gstatic.com; img-src 'self' data:; connect-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`. One middleware adds them to every response, redirects and errors included.

=== Static files

`public/` is embedded with `rust-embed` 8 (`#[folder = "public/"]`; in a debug build it reads the directory, in release it is in the binary). `GET /` serves `index.html`; `GET /admin/` serves `admin/index.html`; `GET /admin` answers 301 `/admin/` as `express.static` did; any other path serves the file of that name or 404 `not_found`. Each file answers `Content-Type` from its extension, `ETag` from rust-embed's SHA-256 of the content, `Cache-Control: public, max-age=0` (Node's `maxAge: 0`), and 304 on a matching `If-None-Match`, so a deploy never mixes old and new modules.

== Signed cookies

One codec in `web/cookies.rs`, keyed by `session.key` (section 7), signs three payloads. A cookie value is

----
base64url(payload) "." base64url(HMAC-SHA256(key, payload))
----

without padding, and `payload` is UTF-8 text with fields joined by `|` (no field can contain `|`: UUIDs, decimal digits and base64url only):

[cols="1,3,1"]
|===
| Kind | Payload | Life

| member | `m\|<user UUID>\|<expires, Unix seconds>\|<csrf: 24 random bytes base64url>` | 30 days
| admin | `a\|<admin UUID>\|<expires>\|<csrf>` | 12 hours
| OIDC | `o\|<state: 32 random bytes b64url>\|<verifier: 32 random bytes b64url>\|<nonce: 16 random bytes b64url>\|<expires>` | 15 minutes
|===

Reading a cookie: split at the last `.`, decode both halves, verify the tag with `hmac`'s `verify_slice` (constant time), parse the payload, check the kind letter and `expires > now`. Any failure makes the request anonymous; nothing distinguishes a forged cookie from an expired one on the wire. The kind letter keeps a member cookie from being replayed as an admin cookie. A value is about 130 bytes for member and admin cookies, about 190 for the OIDC one.

`session.key` is a string of at least 32 characters; its UTF-8 bytes are the HMAC key. Changing it signs everyone out. It is an Erawan secret like the Mongo URI.

What the signed cookie does not give, and the design accepts (_proposed_, article 11): a logout that revokes other devices (Node deleted the row; here each device keeps its cookie until it expires or the user is disabled). A disabled or deleted user is still cut off on the next request, since every request loads the `User` by the cookie's id and refuses when it is missing or has `DisabledAt`.

* One driver call decides and writes: the filter matches only a running session of this activity, so nothing can change between the check and the update. No match falls through to the end-and-insert path above.
* A target is counted from `StartedAt` (the client's reminder fires when the elapsed time passes it), so a target chosen now is stored as the whole seconds already run plus the new target; the reminder then fires the chosen time after the press. A start without a target removes the target (`$unset`), as a new session without one had none.
* A stored target may not pass 86 400 s (a read refuses it), so the filter also requires `StartedAt >= now - (86400 - target) s`. A session too old for the new target does not match, and the request ends it and inserts a new one as before.
* The answer stays `201`, nothing on the wire changes (bylaw 4).
* The radial menu on the timer card's + button (Rux, 2026-11-11) is frontend only: a press on one of its icons sends this same request with `targetMinutes: null`, so a switch from the ring carries no reminder. The ring shows the other activities, predefined first, up to 10; the rest are reached through the start card, which a second press on + opens.
* Not merged: a stop followed later by a start of the same activity (the times do not join), two stored back-to-back sessions made equal by a relabel, and two devices starting the same activity in the same instant with nothing running, where the loser of the insert race ends the winner's session and starts its own.

Other session operations, each one driver call after the usability check where one is needed:

* stop: `findOneAndUpdate { UserId, Running: true } $set EndedAt: now, $unset Running`, return after; `stopped` is the document or null.
* relabel: `findOneAndUpdate { _id, UserId } $set ActivityId`, return after; none → `not_found`. Running or ended alike, as Node allowed.
* delete: `findOneAndDelete { _id, UserId, EndedAt: { $exists: true } }`; none → `findOne { _id, UserId }` to tell `running` (409) from `not_found` (404).
* list: `find { UserId, StartedAt: { $lt: to }, $or: [ { Running: true }, { EndedAt: { $gt: from } } ] }` sorted by `StartedAt`, on the `UserStarted` index.
* state: `find Activity { UserId }` sorted by `CreatedAt` and `findOne TimeSession { UserId, Running: true }`, in parallel (`tokio::join!`).
* create activity: `countDocuments { UserId, DeletedAt: { $exists: false } }` → 50 or more is `too_many`; `countDocuments { UserId }` for the default colour; `insertOne`. No transaction: two devices creating at the same instant can leave 51 (accepted exception 1 in the Bylaws).
* delete activity: `findOneAndUpdate { _id, UserId, DeletedAt: { $exists: false } } $set DeletedAt: now`; none → `not_found`.

=== Admin: setup, login, users

* The first admin: at startup, when `countDocuments Admin` is 0, the service draws 32 random bytes, keeps `SetupToken { token_hash: sha256(token), expires: now + 24 h }` in a `std::sync::Mutex<Option<SetupToken>>` on the facade, and logs the link once at Info: `<public url>/admin/#setup=<token>`. The token is in the fragment, so no request log sees it. `POST /admin/api/setup` validates the credentials, hashes the password (section 2.5), then: `countDocuments Admin` > 0 → `already_set_up`; lock the mutex, compare `sha256(token)` with the held hash in constant time and check `expires > now`, and on a match `take()` the token out of the `Option` → no match → `bad_token`; `insertOne Admin`; the cookie is set. The `take()` under the lock is the single-use step: of two concurrent setups with the one link, one takes the token and inserts, the other gets `bad_token`. If the insert then fails, the token is put back so the link still works. One instance (decisions), so the memory is the only copy; a restart before setup logs a new link, and the old one stops working.
* Login: the throttle is checked first (`locked` 429 with the remaining seconds, rounded up); then `findOne Admin { Username }`; when found, verify the hash, else hash a fixed filler so the time taken does not reveal which names exist; a failure records one against the username, the fifth locks it for 15 minutes; a success clears the username's record and sets the admin cookie.
* The user list: `find User` sorted by `CreatedAt` descending, then one aggregation over `TimeSession` for `lastActive` and `sessionCount` of every user, joined in code. One user's view runs the same aggregation with `$match: { UserId }`.
* Disable: `findOneAndUpdate User { _id } [ { $set: { DisabledAt: { $ifNull: ["$DisabledAt", now] }, UpdatedAt: now } } ]` (a pipeline update keeps an earlier `DisabledAt`, as Node's `coalesce` did), none → `not_found`; then `findOneAndUpdate TimeSession { UserId, Running: true } $set EndedAt: now, $unset Running`. Two writes, this order, no transaction: a crash between them leaves a disabled user with a running session, which the user cannot touch and the enable leaves running; accepted (article 3).
* Enable: `findOneAndUpdate User { _id } $unset DisabledAt, $set UpdatedAt`, none → `not_found`.

== Service shape

A Cargo workspace, edition 2024, version by hand under `[workspace.package]`, every dependency declared once at the root with the reason beside it, as agent-memory's manifest does.

Time bound (article 6, bylaw 2): no single wait exceeds 5 s, except Mongo's server selection at 10 s when the cluster is unreachable, which fails every request at once. The longest request is a start that loses the race twice: the usability check, the continue-running update, then 3 attempts × 2 driver calls = 8 waits, 40 s; the callback is 2 identity-provider calls (3 with a JWKS refetch) and 2 driver calls, 25 s. Both are under bylaw 2's 60 s and far under Cloudflare's 100 s.

Tests, by layer: `model` constructors refuse what section 2.1 says; `storage` conversions accept Node-shaped data and refuse every row of the table in section 2.4; `cookies` round-trips, rejects a changed byte, a wrong kind and an expired payload; `keys` both ways; `web` with a fake facade checks every route's status and JSON against the table in section 3.1, the CSRF rule, the fallbacks, the static files and the headers; `facade` with a fake store checks the start sequence and its retry, the cap and the colour, the setup token and the login throttle. `MongoStore` has no in-process test: no `mongod` runs on the workstation, and copying agent-memory's download-and-run sandbox is work the value did not justify (article 11). It is exercised against the real cluster by `traveler-migrate check` (one transaction, and `OneRunning` refusing a second running insert) and by the cutover's smoke test.

== Data migration

Two tools, both run by hand:

* `scripts/export.mjs`, added to the Node tree for the cutover and deleted with it afterwards (its text is reproduced in the `Dump` doc comment of `traveler-migrate`): `erawan run time-traveler -- node scripts/export.mjs` prints one JSON document to stdout, captured to a local file. It selects `users`, `activities`, `time_sessions` and `admins` with every column, timestamps as ISO strings, and nothing from `auth_sessions`, `admin_sessions`, `admin_setup_tokens` or `oidc_requests`.
* `traveler-migrate`, run from a workstation on Atlas's allow list with the same two secrets in its environment:
** `indexes`: creates every entry of `storage::INDEXES`, idempotent (`createIndexes` with the same name and keys is a no-op; a changed definition is reported, not replaced).
** `check`: runs one empty transaction (start, a `findOne` in it, commit) and inserts then deletes two documents against `OneRunning` to prove the cluster supports what section 5 relies on, then runs the continue-running update on a throwaway session (same activity with a target, another activity, a target past the limit, no target), whose arithmetic happens in the server; reports the outcome.
** `import <dump.json>`: converts every row through the table below into a record, through `TryFrom` into the domain and back, refuses the whole dump when any row is refused (listing each by table and id), refuses a database that already holds a `User` or an `Admin`, then inserts.

[cols="1,2"]
|===
| Postgres row | Document

| `users` | `User`: `_id` = `id`; `Identities: [{ Issuer: AUTH_ISSUER_URL, Subject: oidc_sub }]`, or `{ Issuer: "dev", Subject: "local" }` for `oidc_sub = 'dev:local'`; `Email`, `Name`, `DisabledAt` when not null; `CreatedAt`; `UpdatedAt = created_at`; `hidden_builtins` dropped
| `activities` | `Activity`: `_id`, `UserId`, `Name`, `Color`, `CreatedAt`, `DeletedAt` when not null
| `time_sessions` | `TimeSession`: `_id`, `UserId`, `ActivityId` = the `PREDEFINED` id for a predefined name, the UUID after `c:` otherwise (a key of neither form is a refused row), `StartedAt`, `EndedAt` when not null else `Running: true`, `TargetSeconds` when not null
| `admins` | `Admin`: `_id`, `Username`, `PasswordHash`, `CreatedAt`, `UpdatedAt = created_at`
|===

Cutover, in order: `indexes`; `check`; export; `import`; deploy the Rust image under the same name; sign in, open today, check `/api/state` and the admin list; `erawan addon rm` for `postgres`. Members and the admin sign in again; a running session at export time is imported running.

Done on 2026-11-09: the export ran as the same script inlined through `erawan run time-traveler -- node -e` (base64-encoded, so no Node redeploy was needed), yielding 2 users, 0 custom activities, 103 sessions (1 running) and 1 admin; `import` refused no row; version 19 built from the Dockerfile and went live; Rux signed in and confirmed the data; the `postgres` add-on was removed.
